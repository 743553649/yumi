# StillDive & IdleDive 综合改进方案

## 概述

从**代码质量、参数设计、行为逻辑、文档一致性**四个维度分析改进方向。

---

## 一、参数问题

### A1: StillDive 改用 foreground_max_util 检测 [重要改动]

**现状**: StillDive 用 `core_utils` 的 `max_util`（所有核心中最大的 util）做判定，后台进程随便一动就超阈值，实际很难触发。

**方案**: 改用系统已有的 `foreground_max_util`（eBPF 计算的前台 app 总 CPU 利用率），天然过滤后台噪声。

**具体改动**:
1. `on_load_update()` 签名改为接收 `foreground_max_util: f32`
2. StillDive 的 enter/exit 判定全部改用 `foreground_max_util`
3. 阈值必须下调（`foreground_max_util` 量级比 `max_util` 小很多）：

| 参数 | 当前值 (max_util) | 新值 (fg_max_util) | 理由 |
|------|-------------------|---------------------|------|
| enter_threshold | 0.20 | **0.05** | 前台 app 总 CPU < 5% ≈ 真正空闲 |
| exit_threshold | 0.25 | **0.15** | 前台 app 总 CPU > 15% ≈ 用户在操作 |
| enter_ticks | 10 (2s) | **30 (6s)** | 更长确认窗口，减少误触发 |
| perf_ceil | 0.30 | 0.30 | 不变 |
| smoothing_up | 0.05 | 0.05 | 不变 |
| exit_boost_ticks | 5 | 5 | 不变 |

**滞回带**: 0.05 → 0.15 = 10%（比当前 5% 更宽，更稳定）。

**影响**: `on_load_update` 的调用方（scheduler/mod.rs:427）需同步修改传参。退出条件也从 `max_util > exit_threshold` 改为 `foreground_max_util > exit_threshold`。

### A2: StillDive exit_threshold 滞回带已随 A1 改善

A1 方案的滞回带从 5% 扩大到 10%（0.05/0.15），无需额外调整。

### A3: StillDive perf_ceil=0.30 可能过于激进 [需讨论]

**现状**: 下潜时 perf 上限锁死 30%，意味着 CPU 最多只能跑到最高频率的 30%。

**问题**: 如果手机大核最高 3GHz，下潜后最多 900MHz。用户下拉通知栏、切换 app 等轻操作仍需一定性能，30% 可能导致明显卡顿，直到触摸事件触发退出。

**建议**: 考虑提高到 `0.40~0.50`，或者增加一个"轻活动"阈值——有轻微操作（如滑动）时先退出下潜而非等触摸。

### A4: IdleDive 三个 governor 默认值都是 "menu" [低优先级]

**文件**: `src/idle_dive/config.rs:50-57`

**现状**: normal/diving/doze 三个状态的 cpuidle governor 都默认 "menu"。

**问题**: 切换状态时只是改了 latency 值，governor 本身没变。如果设备支持 `teo` (Timer Events Oriented) governor，它在深度 idle 场景下比 menu 更好。三个状态用同一个 governor 意味着只靠 latency 区分深度，没有充分利用 governor 策略差异。

**建议**: 默认值可改为 `normal="menu", diving="teo", doze="teo"`，或者保持现状但文档说明用户可以按设备调整。

### A5: IdleDive exit_delay_ms=30 过于灵敏 [低优先级]

**现状**: 退出下潜只需 avg_util > exit_threshold 持续 30ms。

**问题**: 30ms 非常短，一次短暂的后台任务唤醒就可能触发退出。而进入下潜需要 500ms，退出不对称可能导致频繁状态切换。

**建议**: 提高到 `50~100ms`，与进入延迟形成更合理的不对称比（进入慢退出快，但不要快到过敏）。

## 二、行为逻辑问题

### B1: StillDive 与 IdleDive 检测指标已统一 [随 A1 解决]

A1 改用 `foreground_max_util` 后，StillDive 关注"前台 app 是否空闲"，IdleDive 关注"系统整体 CPU 是否空闲"。两者分工更清晰：
- StillDive → 前台 app 空闲 = 用户没在操作 → 压频
- IdleDive → 系统整体空闲 → 加深 C-state

### B2: IdleDive DozeDiving 进入无防抖 [可改进]

**文件**: `src/idle_dive/controller.rs:96-99`

**现状**: `enter_doze()` 直接 `transition_to(DozeDiving)`，无任何延迟或条件检查。`exit_doze()` 直接 `transition_to(Normal)`。

**问题**: 如果屏幕状态事件抖动（快速亮灭屏），会导致 IdleDive 在 Normal ↔ DozeDiving 间快速切换，每次都触发 sysfs 写入和 PM-QoS 更新。

**建议**: 添加简单的防抖——记录上次 doze 进入时间，如果距离上次退出不到 500ms 则跳过。

### B3: StillDive 退出 boost 期间 smoothing_up 阶跃 [可改进]

**文件**: `src/scheduler/cpu_load_governor.rs:392-398`

**现状**: 退出 StillDive 时 `smoothing_up` 从 0.05 瞬间跳到 1.0（exit_boost），5 tick 后骤降回默认值 0.60。

**问题**: 频率先被瞬间拉高（1.0 加速），然后突然降回正常升频速率，形成频率曲线上的"阶梯"。

**建议**: boost 期间线性衰减：
```rust
if self.still_exit_boost > 0 {
    let base = self.cfg.smoothing_up;
    let progress = 1.0 - (self.still_exit_boost as f32 / sd.exit_boost_ticks as f32);
    base + (1.0 - base) * progress  // 从 1.0 线性降到 base
}
```

### B4: IdleDive Diving → DozeDiving 跳过中间状态 [设计观察]

**文件**: `src/idle_dive/controller.rs:96-99`

**现状**: 如果当前处于 Diving 状态，息屏时直接跳到 DozeDiving，亮屏后直接回到 Normal（跳过 Diving）。

**影响**: 亮屏后即使 CPU 仍然空闲，也需要重新走 500ms 的 dive_delay 才能回到 Diving。这期间 CPU 处于无保护的正常状态。

**建议**: 亮屏退出 Doze 时，如果 avg_util 仍低于 dive_threshold，直接回到 Diving 而非 Normal。

## 三、代码质量问题

### C1: LatencyWriter 错误传播是假的 [small]

**文件**: `src/idle_dive/latency.rs:100-109, 112-140`

`set_governor()` 和 `set_latency()` 内部 warn 了错误但永远返回 `Ok(())`。controller 的 `if let Err(e)` 永远不触发。

**方案**: 全部路径写入失败才返回 `Err`，部分失败 warn + `Ok`。

### C2: StillDive 状态散落在 CLG 上 [small]

**文件**: `src/scheduler/cpu_load_governor.rs:115-118`

`still_mode`/`still_low_ticks`/`still_exit_boost` 是 CLG 的直接字段，违反关注点分离。

**方案**: 提取为 `StillDiveRuntime` struct，CLG 持有 `Option<StillDiveRuntime>`。

### C3: IdleDive transition_to 重复代码 [small]

**文件**: `src/idle_dive/controller.rs:121-157`

三分支各自手写 `set_governor` + `set_latency`。

**方案**: 用 `(governor, latency)` 元组查表 + 统一调用。

### C4: max_util 重复计算 [small]

**文件**: `src/scheduler/cpu_load_governor.rs:357, 491`

每 25 tick 的 debug 日志重新 fold 一次 `max_util`。

**方案**: 提升为局部变量贯穿整个 `on_load_update`。

### C5: LatencyWriter 路径用 String 而非 PathBuf [small]

**文件**: `src/idle_dive/latency.rs:28-29`

**方案**: `Vec<String>` → `Vec<PathBuf>`。

### C6: i18n 日志 key 语义不准确 [small]

**文件**: `src/idle_dive/latency.rs:91, 103, 122, 132`

四个不同的错误场景（open PM-QoS 失败、write PM-QoS 失败、set governor 失败、set latency 失败）全部复用 `"sysfs-open-failed"` 这个 key。

**方案**: 新增专用 key：`"pm-qos-open-failed"`, `"pm-qos-write-failed"`, `"idle-dive-set-governor-failed"`, `"idle-dive-set-latency-failed"`（后两个已存在于 controller.rs 但 latency.rs 没用）。

## 四、文档不一致

### D1: README StillDive 描述需随 A1 更新 [必修]

README line 128 写 "CPU 负载 <8%"，line 139 写 `enter_threshold: 0.08`。A1 改用 `foreground_max_util` 后，需更新为"前台 app CPU 利用率 <5%"，阈值改为 `0.05`。同时说明检测逻辑从"所有核心最大值"变为"前台 app 总利用率"。

### D2: README IdleDive 描述有误 [必修]

README line 117 写 `CPU idle >12%`，但实际是 CPU **utilization** < 12%（即 idle > 88%）。"idle > 12%" 容易误解为"CPU 空闲比例超过 12%"，与实际逻辑相反。

### D3: 设计文档需随 A1 更新 [必修]

`docs/CPU静止下潜-一步到位综合方案.md` 中的检测逻辑描述和阈值都需要更新为 foreground_max_util 版本。
