## AI 执行须知（新会话必读）

本文件是 AI 的执行手册。新会话接手时按以下规则执行，不要偏离。

**单任务闭环**（每个任务必须走完四步才算完成）：
1. **改**：按本文件对应任务的"方案"改代码
2. **验**：`$env:YUMI_SKIP_EBPF="1"; cargo check --target aarch64-linux-android`（Windows PowerShell）。此项目面向 Android，host `cargo check` 会因 `netlink-sys` 缺 Linux 类型失败，**必须带 `--target aarch64-linux-android`**。测试任务用 `cargo test --target aarch64-linux-android --lib`

**批次策略**：29 个任务分 10 批（见文末"批次划分"）。每批开新分支 `fix/bN-xxx`，做完一批**停下汇报用户**，由用户决定合并回 main 再开下一批。**禁止一个会话连跑多批**——上下文过长会导致后半段质量下降。

**新会话接续方法**：不用重读历史对话。只需 (1) 读本文件的 checkbox，找到第一个 `[ ]` 任务；(2) `git log --oneline -10` 看最近进度；(3) 从该任务继续。

### FIX-012 添加 IPC 连接数限制 `[x]`

**问题**：[ipc_server.rs:42-57](file:///c:/Users/GUDGA/yumi/src/ipc_server.rs#L42) 的 `start_with_listener` 每个连接直接 `std::thread::spawn`，无并发上限。已有 `set_read_timeout(10s)`（[L68](file:///c:/Users/GUDGA/yumi/src/ipc_server.rs#L68)）部分缓解，但线程数仍无上限。

**方案**：

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
const MAX_CONCURRENT_CONNECTIONS: usize = 8;
static ACTIVE_CONNECTIONS: AtomicUsize = AtomicUsize::new(0);

// accept 循环内：
let current = ACTIVE_CONNECTIONS.load(Ordering::Relaxed);
if current >= MAX_CONCURRENT_CONNECTIONS {
    log::debug!("IPC rejected: max {} connections", MAX_CONCURRENT_CONNECTIONS);
    drop(stream);
    continue;
}
ACTIVE_CONNECTIONS.fetch_add(1, Ordering::Relaxed);
std::thread::spawn(move || {
    handle_client(stream, tx, root, config_arc, force_refresh_arc);
    ACTIVE_CONNECTIONS.fetch_sub(1, Ordering::Relaxed);
});
```

**验证**：`cargo check` 通过；并发 9 连接时第 9 个被拒绝并记录 debug 日志。

**执行记录**（2026-08-05，与文档描述的差异，以实际代码为准）：
- [ipc_server.rs](file:///c:/Users/GUDGA/yumi/src/ipc_server.rs) `start_with_listener` 的 accept 循环加并发上限：`const MAX_CONCURRENT_CONNECTIONS: usize = 8` + `static ACTIVE_CONNECTIONS: AtomicUsize`。
- **名额抢占用 `fetch_add` 后检查**（`prev >= MAX` 则 `fetch_sub` 回退 + `continue` + debug 日志），替代文档示例的"先 `load` 再 `fetch_add`"——后者有 TOCTOU 竞态（多线程同时通过检查会短暂超限），`fetch_add`-后检查是无锁原子的，且代码更短。
- **新增 `ConnectionGuard`（Drop 时 `fetch_sub`）**：文档示例把 `fetch_sub` 直接写在 `handle_client(...)` 之后，若 `handle_client` panic 则计数永不回退，长期运行会泄漏名额直至 IPC 被永久堵死——这正违背 FIX-012 的健壮性目标。改用 guard 后，闭包正常返回或 panic unwind 都会触发 `Drop` 回退计数。
- **不处理 `thread::spawn` 失败**：`std::thread::spawn` 返回 `JoinHandle<T>` 而非 `Result`（失败直接 panic=OOM，无法用 `is_err` 处理；首版照搬"spawn 失败回退"思路导致 `E0599 no method is_err` 编译错误，已移除）。spawn panic 属灾难性 OOM，accept 线程本身会挂，计数泄漏无意义；guard 已覆盖真实的 `handle_client` panic 场景。
- `Ordering::Relaxed`：连接计数仅作软上限近似，不参与其他同步，Relaxed 足够。
- `handle_client` 原有 10s `set_read_timeout` 保留，与并发上限形成"慢连接超时 + 连接数封顶"双重兜底。
- 验证：`cargo check --target aarch64-linux-android` 通过；`cargo clippy` 无新增 warning（39 个预存 warning 与本任务无关，唯一命中 ipc_server.rs 的是 L153 `process_command` 的 `&PathBuf` 签名，预存）。第 9 连接被拒逻辑：`fetch_add` 返回 `prev=8 ≥ 8` → 回退 + debug 日志（设备实测待联机）。
