## 阶段六：CPU 静止下潜 (Idle Dive) (2026-08-01)

> 实现方案: `docs/TouchBoost实现方案.md` 中 "CPU 静止下潜实现方案" 部分

### 功能概述
- **功能**: CPU 平均负载极低时，通过切换 cpuidle governor 并放宽 `latency_us` 上限，让 CPU 进入更深的 C-state 空闲状态，降低日用轻负载与息屏待机功耗
- **方案**: 文档中的方案 A (cpuidle governor 切换 + latency 参数调整)

### 新增文件
- `src/idle_dive/mod.rs` — IdleDive 模块（`IdleDiveConfig` 配置结构 + `IdleDiveController` 控制器 + 4 个单元测试）
- `module/config/idle_dive.yaml` — 运行时配置（扁平顶层结构，无包装键）

### 修改文件
- `src/main.rs` — 注册 `idle_dive` 模块
- `src/scheduler/mod.rs` — 集成:
  - 加载 idle_dive 共享配置 (Arc\<RwLock\>，config watcher 热重载，与 cpuset 模式一致)
  - IPC 线程内创建 `IdleDiveController` 并 init（探测 cpuidle 节点，失败仅告警不影响主流程）
  - `ScreenStateChange` 息屏 → `enter_doze()`，亮屏 → `exit_doze()`
  - `SystemLoadUpdate` → 计算 core_utils 平均负载投喂 `update(avg_util)`（200ms 一个 tick）
- `module/config/i18n/zh.ftl` + `en.ftl` — 新增 6 个 IdleDive 翻译键

### 状态机设计
| 状态 | 进入条件 | 退出条件 |
|:---|:---|:---|
| Normal | 初始状态 | 平均负载 < dive_threshold 持续 dive_delay_ms |
| Diving | 上述条件满足 | 平均负载 > exit_threshold 持续 exit_delay_ms |
| DozeDiving | 息屏事件 | 亮屏事件 |

### 关键设计要点
- **配置扁平化**: 吸取 cpuset.yaml C1 教训（包装键导致配置永远加载默认值），idle_dive.yaml 顶层直接为 `enabled`/`governors`/`params` 等键
- **容错**: cpuidle 节点不存在或写入器无效时 `init()` 失败，控制器保持不可用，主流程不受影响
- **集成方式**: 复用 IPC 主线程事件循环（无需独立线程/通道），与 cpuset_manager 一致
- **默认参数**: dive_threshold 0.15 / exit_threshold 0.30 / dive_delay 2s / exit_delay 500ms；normal latency 100μs、diving 500μs、doze 1000μs

### 验证状态
- ✅ `cargo check` 编译通过（YUMI_SKIP_EBPF=1 本地检查）
- ✅ 新增代码无 clippy 警告
- ✅ 4 个单元测试全部通过（配置解析 x2、状态机 x2）
- ⏳ 设备实测待验证（需 GitHub Actions 交叉编译后刷机测试）

### 注意事项
- 部分平台 `/sys/devices/system/cpu/cpuidle/latency_us` 可能不存在，此时功能自动禁用（有日志提示）
- latency_us 值越大允许的 C-state 越深，唤醒延迟越大，需在省电与响应间权衡

### 代码审查与修复 (2026-08-01)

使用 compose:review 审查后修复：

**I1 (Important)**: 禁用配置时状态机"卡死"，sysfs 残留非正常配置
- 问题: `update/enter_doze/exit_doze` 在 `!enabled` 时直接 return，Diving/DozeDiving 中禁用后状态永久卡死（如 DozeDiving 亮屏也不恢复）
- 修复: 新增 `sync_enabled()` 检测"启用→禁用"边沿，清理状态并恢复 normal 配置；`exit_doze()` 无条件恢复状态（写入按 enabled 门控）；补充 2 个回归测试

**I2 (Important)**: 启动时无条件接管 cpuidle 节点
- 问题: `init()` 不检查 `cfg.enabled` 就写入 normal 配置；`enabled: false` 时启动仍改写 sysfs 一次
- 修复: init 时 enabled=false 不写任何节点；新增 `Drop` impl 优雅退出时恢复 normal 配置兜底

**I3 (Important)**: 空 `core_utils` 归零人为制造下潜触发
- 问题: `core_utils.is_empty() → avg_util=0.0`，eBPF 数据故障时 0.0 恒低于 dive_threshold，屏亮时误触发深度省电
- 修复: scheduler/mod.rs 空向量时跳过 `idle_dive.update()`，而非合成 0.0

**M1 (Minor)**: 设计文档 YAML 示例带 `idle_dive:` 包装键（会导致配置加载默认值）
- 修复: 修正 `docs/TouchBoost实现方案.md` 示例 + 补充集成方式实现说明

- **功能**: 用户触摸屏幕时临时提升 CPU scaling_min_freq，确保触摸操作响应速度；松手后频率逐步衰减恢复
- **方案**: epoll 直接监听 `/dev/input/event*` 设备，比 Android 框架层更快捕获触摸事件

### 新增文件
- `src/touch_boost/mod.rs` — TouchBoost 模块（`TouchBoostConfig` 配置 + `TouchBoostController` 状态机 + `TouchListener` epoll 监听器 + 4 个单元测试）
- `module/config/touch_boost.yaml` — 运行时配置（扁平顶层结构）

### 修改文件
- `src/main.rs` — 注册 `touch_boost` 模块
- `src/scheduler/mod.rs` — 集成:
  - 加载 touch_boost 共享配置 (Arc\<RwLock\>，config watcher 热重载)
  - IPC 线程内获取 CPU policies，创建 channel，启动 TouchBoost 监听线程
  - 非阻塞 `try_recv` 处理触摸事件（预留 FAS/CLG 联动接口）
- `module/config/i18n/zh.ftl` + `en.ftl` — 新增 10 个 TouchBoost 翻译键

### 状态机设计
| 状态 | 进入条件 | 退出条件 |
|:---|:---|:---|
| Idle | 初始状态 / 恢复完成 | 触摸按下 (ABS_MT_TRACKING_ID != -1) |
| Touching | 触摸按下 | 松手 (ABS_MT_TRACKING_ID == -1) 且超过 min_boost_duration_ms |
| Recovering | 松手 | release_delay_ms 后衰减恢复完成 / 再次触摸 |

### 关键设计要点
- **独立线程**: TouchListener 使用 epoll 阻塞等待，运行在独立线程，通过 mpsc channel 向 IPC 线程推送触摸状态
- **配置扁平化**: 与 cpuset.yaml/idle_dive.yaml 一致，顶层直接为 enabled/boost_freqs 等键
- **设备自动检测**: 扫描 /sys/class/input/event*/capabilities/abs 检测支持 ABS_MT_TRACKING_ID 的触摸设备
- **容错**: 触摸设备不存在时仅告警，不影响主流程；配置缺失时使用默认值
- **频率控制**: 仅修改 scaling_min_freq，不修改 max_freq，与 FAS/CLG 无冲突
- **衰减恢复**: 松手后按 recover_decay 比例逐步降低 boost 频率，平滑过渡

### 默认参数
- boost_freqs: [2500000, 0, 2000000] (Policy 0 超大核 2.5GHz, Policy 2 大核 2.0GHz)
- release_delay_ms: 100 (松手后 100ms 开始恢复)
- recover_decay: 0.15 (每次 tick 降低 15%)
- min_boost_duration_ms: 50 (最短 boost 50ms 防误触)
